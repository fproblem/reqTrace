# ReqTrace

Инструмент отслеживания покрытия требований тестами для QA-команд, работающих
с требованиями в Confluence и тестами в Jira.

ReqTrace подключается к Confluence, хранит снимки страниц требований и
позволяет выделять фрагменты текста («привязки») и связывать их с ключами
тестов из Jira. Когда требования меняются, ReqTrace сам замечает это ночным
прогоном, переносит привязки на новую версию текста, помечает задетые —
и утром рассказывает команде, какие тесты нужно перепроверить.

**Ключевая идея:** привязка — это маркер в тексте конкретного снимка страницы
(модель inline-комментариев Confluence). Статус привязки меняют только два
события: реальное изменение текста под маркером (сервер переносит маркер
диффом «старый снимок → новый») и явное решение человека. Никакого «поиска
текста по странице» не существует — самопроизвольное «устаревание» или
«прыгающие» подсветки невозможны по построению.

## Возможности

### Страницы и требования
- **Дерево страниц** из спейсов Confluence: добавление по URL, автоматическая
  синхронизация структуры (перемещения, новые и удалённые страницы),
  виртуальные страницы-родители.
- **Снимки и baseline:** каждая версия страницы сохраняется снимком; baseline
  фиксирует «согласованную» версию, вкладка «Изменения» показывает дифф
  baseline → текущий снимок.
- Рендер контента максимально близок к Confluence: таблицы с горизонтальной
  прокруткой и тенями краёв, макросы, статус-лейблы, картинки с
  резервированием места (без сдвигов раскладки при загрузке).

### Привязки и статусы
- Выделение произвольного фрагмента текста → привязка ключей тестов к нему.
- Статусы: **Актуально** / **Требует проверки** (текст под маркером изменился;
  в панели — пословный дифф цитаты) / **Утрачено** (не уцелел ни один символ;
  терминальный статус — тесты привязываются заново).
- «Актуализировать» — человек подтверждает новый текст под маркером.
- Ссылка на конкретную привязку (`?highlight=…`) — для вставки в Jira-задачи.
- Индикатор покрытия страницы и счётчики статусов в шапке, циклическая
  навигация по привязкам каждого статуса.

### Экран «Тесты» (реверс-индекс)
- «Тест → какие требования он держит»: два яруса — карточки проектов и
  список ключей с привязками, цитатами и статусами.
- **Названия тестов из Jira** по личному токену (PAT): валидация ключа при
  привязке («Тест не найден в Jira»), ночная синхронизация имён.
- Мгновенный поиск по ключу и названию, фильтры по статусам, диплинки.
- Список приезжает лёгким (цитаты подтягиваются при раскрытии строки) —
  экран готов к тысячам тестов.

### Автообновление и дайджест
- **Ночной прогон** (по умолчанию 03:00 МСК): перепроверка подключений →
  синхронизация деревьев → обновление страниц → перенос привязок →
  синхронизация названий тестов. Журнал прогонов хранится 90 дней.
- **Самолечение:** проекты, оставшиеся без успешного прогона (VPN, сеть),
  добираются каждый час; страницы, упавшие точечно (таймаут на тяжёлой
  странице), перечитываются отдельно, не дожидаясь следующей ночи.
- **Ручной запуск** «Обновить страницы сейчас» с карточки проекта; живой
  индикатор идущего прогона у колокольчика.
- **Дайджест уведомлений:** что изменилось, какие привязки задеты, какие
  тесты затронуты, какие страницы не обновились (поимённо) и когда будет
  повторная попытка. События сгруппированы по дням; записи об ошибках ведут
  чинить подключение, записи с находками — на экран «Тесты».

### Доступ и безопасность
- **Вход только через Google** (ID-token flow) с ограничением по домену
  почты; сессия — JWT в HttpOnly-cookie (SameSite=Lax, Secure в проде).
- **Мультипроектность с личными кредами:** каждый участник подключается к
  Confluence своими логином/паролем (и опционально Jira-токеном); секреты
  хранятся в БД зашифрованными (Fernet, ключ вне БД — в `.env`).
  Членство в проекте = наличие кред; контент проекта виден только участникам.
- ReqTrace **ничего не пишет** во внешние системы: к Confluence и Jira —
  только чтение (у Jira-интеграции это контракт: в коде существуют только
  GET-запросы).

## Архитектура

```
Браузер ──► frontend (nginx :3000→80)
              ├── статика React-приложения
              └── /api/* ──► backend (FastAPI :8000)
                               ├── PostgreSQL 16 (:5432, volume pgdata)
                               ├── Confluence Server API (личные креды, GET)
                               ├── Jira REST API (личные PAT, только GET)
                               └── Google (проверка ID-токена при входе)
```

| Компонент | Технология |
|---|---|
| Frontend | React 18 + TypeScript (CRA), nginx |
| Backend | Python 3.12, FastAPI, async SQLAlchemy 2, Alembic |
| БД | PostgreSQL 16 |
| Планировщик | asyncio-задача в lifespan бэкенда (advisory-lock Postgres) |
| Развёртывание | Docker Compose (3 контейнера) |

Миграции БД применяются автоматически при старте контейнера бэкенда
(`alembic upgrade head`). Health-check: `GET /api/health`.

Весь код приложения — в `reqtrace/`; живые дизайн-документы — в `docs/`;
идеи и отложенные решения — в `BACKLOG.md`.

## Быстрый старт

Понадобятся: Docker (Compose v2), Client ID Google OAuth (тип Web
application; в Google Cloud Console добавьте origin, с которого открывается
приложение) и доступ к вашему Confluence.

```bash
git clone <репозиторий> && cd <клон>/reqtrace

# 1. Секреты (без .env компоуз не стартует)
cp .env.example .env
# заполните: POSTGRES_PASSWORD, GOOGLE_CLIENT_ID,
#   SESSION_SECRET   ← openssl rand -hex 32
#   CREDENTIALS_KEY  ← python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
# прод-машина: дополнительно COMPOSE_PROFILES=prod и сертификаты в certs/

# 2. Запуск
docker compose up -d --build
```

Приложение: в проде — **https://\<ваш домен\>** (nginx на 80/443); на
дев-машине фронтенд-контейнер не поднимается — запустите `npm start` в
`reqtrace/frontend` и открывайте **http://localhost:3000** (API: :8000,
Postgres: :5432). Подробнее о ролях машин — раздел «Полигон и прод».

Первые шаги в приложении: вход Google-аккаунтом разрешённого домена →
«Профиль и проекты» → создать/присоединиться к проекту, введя свои креды
Confluence (и Jira-токен, если хотите видеть названия тестов) → добавить
страницы требований в дерево. Встроенная инструкция — модалка «Как работает
ReqTrace» в профиле.

## Конфигурация (`reqtrace/.env`)

| Переменная | Значение |
|---|---|
| `COMPOSE_PROFILES` | роль машины: `prod` — офисный стенд (фронт на 80/443 с сертами), `preview` — смоук прод-сборки без TLS на :3000; не задана — дев-набор postgres+backend |
| `POSTGRES_PASSWORD` | пароль БД (используется компоузом и бэкендом) |
| `GOOGLE_CLIENT_ID` | Client ID Google OAuth (не секрет) |
| `SESSION_SECRET` | ключ подписи сессионных JWT — `openssl rand -hex 32` |
| `CREDENTIALS_KEY` | Fernet-ключ шифрования кред участников. ⚠ Потеря/смена = сохранённые пароли нечитаемы, участники вводят заново |
| `ALLOWED_EMAIL_DOMAIN` | домен почты, которому разрешён вход (например, `surf.dev`) |
| `SESSION_TTL_DAYS` | время жизни сессии, дней (по умолчанию 7) |
| `COOKIE_SECURE` | `true` в проде (https), `false` на локальном http |
| `AUTO_REFRESH_ENABLED` | ночное автообновление (по умолчанию `true`) |
| `AUTO_REFRESH_AT` / `AUTO_REFRESH_TZ` | время старта прогона в указанной зоне (по умолчанию `03:00` `Europe/Moscow`) |
| `AUTO_REFRESH_PAGE_DELAY_MS` | пауза между запросами к Confluence в прогоне (по умолчанию 300) |

## Полигон и прод

Проект живёт на двух машинах с разными ролями; между ними через git едет
**только код** — данные и `.env` не синхронизируются никогда (разные
`CREDENTIALS_KEY` делают перенос кред невозможным по построению).

- **Дев-машина («полигон»)** — тестовые данные, свои секреты,
  `COOKIE_SECURE=false`, без `COMPOSE_PROFILES`. Запуск одной командой:
  `./dev.sh` из корня клона — проверит окружение, поднимет
  postgres+backend с пересборкой, дождётся health и запустит фронт
  дев-сервером (hot reload; Ctrl+C останавливает только фронт). Смоук
  прод-сборки перед релизом: `COMPOSE_PROFILES=preview docker compose up
  -d --build frontend-dev` → http://localhost:3000.
- **Прод-машина (офис)** — боевые данные, свои секреты,
  `COMPOSE_PROFILES=prod` в `.env`, сертификаты в `reqtrace/certs/`.
  Всегда чистое рабочее дерево на `main`; единственная ручная команда —
  `./update.sh`. Разработки на проде нет; вынужденная правка на месте —
  коммит и пуш сразу же.
- **Поток релиза:** ветка `release/vX.Y.Z` на полигоне → тесты → merge в
  `main` + аннотированный тег `v.X.Y.Z` → push → `./update.sh` на проде.
  Хотфикс — тот же путь.

## Обновление и откат

- **Обновление одной командой:** `./update.sh` из корня клона — проверяет
  окружение, показывает входящие коммиты и предупреждает о миграциях, делает
  бэкап БД в `backups/` (хранятся последние 10), `git pull --ff-only`,
  пересборка контейнеров, ожидание health-check.
- **Релизы и откат:** каждый релиз помечен аннотированным git-тегом
  `v.X.Y.Z`. Откат: `git reset --hard v.X.Y.Z` + пересборка; если релиз нёс
  миграции — соответствующий `alembic downgrade` (указан в сообщении тега)
  и/или восстановление бэкапа БД.
- История изменений для пользователей — кнопка версии в шапке приложения
  (`reqtrace/frontend/public/changelog.json`).

## Эксплуатация

- **Данные:** только Postgres (docker volume `pgdata`) — снимки страниц,
  привязки, зашифрованные креды, журнал прогонов (ретеншн 90 дней).
  Бэкап: `docker compose exec postgres pg_dump -U reqtrace reqtrace`.
- **Сеть:** входящий трафик — только на frontend (nginx, отдаёт статику и
  проксирует `/api/`); исходящий — Confluence, Jira, Google (см. схему).
  Всё API, кроме `/api/auth/*` и `/api/health`, закрыто сессией.
- **Машине с бэкендом ночью нужны:** доступ к Confluence (VPN, если он
  требуется) и бодрствование в момент прогона; впрочем, пропущенная ночь
  навёрстывается при старте, а недоступность Confluence лечится почасовым
  добором.

### Чек-лист прод-развёртывания

1. Свежие `SESSION_SECRET` и `CREDENTIALS_KEY` (не с тестовых стендов;
   перенос существующей БД дампом требует ТОГО ЖЕ `CREDENTIALS_KEY`).
2. HTTPS перед nginx-фронтом + `COOKIE_SECURE=true` (на голом http cookie
   не поставится).
3. Прод-origin добавлен в Google Cloud Console у OAuth-клиента — иначе
   кнопка входа не работает.
4. Бэкапы БД: регулярные + обязательно перед обновлениями с миграциями
   (`update.sh` делает автоматически).
5. `ALLOWED_EMAIL_DOMAIN` — домен вашей организации.

## Разработка

```bash
# Тесты бэкенда (python на хосте не нужен)
cd reqtrace && docker compose run --rm --no-deps -v "$(pwd)/backend:/app" backend \
  python -m unittest discover tests

# Фронтенд
cd reqtrace/frontend
CI=true npm test        # тесты
npx tsc --noEmit        # типизация
npm start               # dev-сервер

# Git-хуки (обязательный changelog у feat/fix в релизных ветках)
git config core.hooksPath .githooks
```

Конвенции: релизные ветки `release/vX.Y.Z` (по одной теме на релиз), записи
в changelog добавляются тем же коммитом, что и фича; версия приложения —
первый блок `changelog.json`. Дизайн-документы ключевых подсистем — в
`docs/` (модель привязок — `anchoring-plan-v1.5.9.md`, автообновление —
`auto-refresh-plan-v1.6.md`); гайд для ИИ-ассистента — `CLAUDE.md`.
