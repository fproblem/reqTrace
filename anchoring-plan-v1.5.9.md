# План v1.5.9 — переписывание логики привязок «как inline-комментарии Confluence»

Статус: РЕАЛИЗОВАН 2026-07-08 (этапы 1–7; коммиты 819b7e55, a89b2eca, cbb639bb,
0b233635, ef17c9aa + докоммиты этапа 7). Живой сквозной прогон на полигонной
странице пройден (создание → верификация → «Требует проверки» → тест →
«Актуализировать» → «Актуально» → удаление). Утверждён пользователем с
уточнением: «Утрачено» — полностью терминальный статус. Никакого восстановления/перепривязки утраченных привязок не
делаем вообще (ни авто, ни ручного, ни «догадок»): утраченная привязка означает,
что требование в прежнем виде исчезло — тесты перепривязываются к новой привязке.
Исследование эталона проведено 2026-07-08 (9 веб-агентов, 5 направлений +
4 адверсариальные проверки; ключевые источники — в конце).

## 1. Как на самом деле устроен эталон (проверенные факты)

1. **Якорь — физическая метка в теле документа**, а не сохранённый «поиск».
   Storage XHTML: `<ac:inline-comment-marker ac:ref="UUID">текст</ac:inline-comment-marker>`;
   в ADF — mark `annotation {id, annotationType: inlineComment}`. Комментарий-объект
   живёт отдельно и связан с маркером по UUID.
2. **Confluence никогда не переискивает текст.** Сопоставление по цитате происходит
   ровно один раз — при создании (`textSelection + matchCount + matchIndex` в API v2);
   дальше маркер «едет» сквозь правки внутри модели редактора (ProseMirror marks,
   позиции трансформируются через StepMap, а не ищутся). Подтверждено от противного:
   PUT тела без маркеров отрывает ВСЕ комментарии, даже если текст байт-в-байт тот же.
3. **Частичная правка внутри выделения** → маркер сжимается/расширяется, комментарий
   остаётся на уцелевшем/изменённом тексте. Исходная цитата (`inlineOriginalSelection`)
   при этом НЕ пересчитывается — замороженный снимок на момент создания.
4. **Решение «жив/утрачен» принимается один раз при публикации версии**: Confluence
   сравнивает предыдущую и новую версии; размеченный текст исчез → комментарий
   авто-резолвится со статусом **dangling** (не resolved). Статусы: open, reopened,
   resolved, dangling. Dangling — терминальный: из UI не переоткрывается, повторный
   набор того же текста НЕ возвращает комментарий.
5. **Перемещение текста (cut/paste) = удаление** → dangling. Эталон НЕ устойчив
   к переносам (CONFSERVER-42726 открыт с 2016). Копирование страницы комментарии
   не переносит.
6. **Ручное восстановление — первоклассная операция** (Cloud, с 05.2024):
   Restore comment → выделить текст заново → комментарий перепривязан.
7. Прикладной опыт (Hypothes.is, W3C, Brush et al. CHI 2001, GitLab PositionTracer):
   пользователи ждут честного «Утрачено» при удалении текста; уверенно-неверное
   размещение хуже орфана; показ «догадки» ускоряет ручную перепривязку; перенос
   через дифф версий детерминирован и дёшев — и это ровно наша ситуация, потому что
   ОБЕ версии текста у нас есть локально (снимки).

## 2. Главный вывод

Текущая модель ReqTrace («цитата + пересопоставление при каждой отрисовке») — это
модель, которой у эталона НЕТ; именно она порождала «прыгающие» подсветки и
самопроизвольные статусы. Эмулировать эталон read-only-средствами можно точно:

> **Маркер живёт в наших снимках.** Привязка = диапазон в тексте конкретного
> снимка. При каждом refresh диапазон ОДИН РАЗ переносится диффом
> «старый снимок → новый снимок» (дифф реконструирует правки редактора, через
> которые Confluence протаскивает маркер). Фронтенд ничего не ищет и статусов
> не решает — он рендерит готовые координаты.

## 3. Целевая модель

### Данные привязки
- `original_quote` — замороженная цитата (аналог inlineOriginalSelection);
  обновляется ТОЛЬКО человеком («Актуализировать»/«Перепривязать»). Сейчас это text_content.
- `anchored_text` — НОВОЕ ПОЛЕ: текущий текст под маркером в актуальном снимке
  (пересчитывается при refresh). Для панели: дифф original_quote ↔ anchored_text.
- Якорь: `anchor_block_start/end + start/end_char_offset` в координатах
  ОБРАБОТАННОГО HTML актуального снимка (`snapshot_id` уже есть) + абсолютные
  смещения в полном тексте (вычислимы из блочных — хранить не обязательно).
- Удаляем мёртвые поля start_xpath/start_offset/end_xpath/end_offset (legacy v1).
- text_before/text_after остаются только как контекст для дизамбигуации при
  СОЗДАНИИ и «догадки» для утраченных — в переносе не участвуют.

### Статусы и переходы (полная таблица; фиксируется тестами)
Статусы прежние: `active` («Актуально»), `outdated` («Требует проверки»),
`lost` («Утрачено» = dangling).

| Событие | Переход |
|---|---|
| Создание | → outdated (продуктовое решение: новая привязка ждёт подтверждения) |
| Refresh: диапазон перенёсся, текст == original_quote (по normalize) | статус НЕ меняется |
| Refresh: диапазон перенёсся, текст изменился | active → outdated; outdated остаётся |
| Refresh: диапазон не выжил (текст удалён/заменён целиком/перемещён) | любой → lost |
| «Актуализировать» (человек, outdated) | original_quote := anchored_text → active |
| Фронтенд | статусы НЕ пишет вообще |

lost — терминальный статус без переходов из него (решение пользователя):
утраченные привязки не проецируются, не восстанавливаются и не перепривязываются;
они остаются в секции «Утраченные» как сигнал «перепривяжите тесты заново».

Отличия от v1.5.8 (сознательные):
- **Восстановление lost убирается целиком** (Confluence-identical: dangling
  терминален; Brush: пользователи не хотят «умного» возврата).
- **Частичное 50%-совпадение v1.5.8 убирается**: его роль выполняет перенос диффом
  (правка внутри выделения сжимает/растит диапазон механически, без порогов похожести).
- Статусы меняются ТОЛЬКО при refresh и ручных действиях — класс багов
  «самоустаревания при просмотре» (v1.5.7) исчезает по построению.

### Движок переноса (`backend/app/services/anchoring.py`, чистые функции)
1. Документная модель: render_page_html → СЕГМЕНТЫ (уточнение по ручному
   тесту §6): собственный текст каждого блочного элемента — сегмент; у
   родительского пункта списка/ячейки с вложенными блоками свой текст даёт
   отдельный сегмент перед вложенными (в чисто листовой модели такой текст
   вообще не существовал, и выделения на нём были невозможны). Полный текст +
   двунаправленная карта «сегмент/смещение ↔ абсолютное смещение» (урок
   Hypothes.is: все позиции живут в одном строковом пространстве).
   ⚠ Смещения во внешних якорях — UTF-16 code units (родное пространство DOM;
   эмодзи вне BMP = 2 юнита), внутри движка — кодпоинты с конвертацией на
   границе (уточнение по ручному тесту: эмодзи в сегменте сдвигали координаты).
   Нормализация формализуется: NFC, невидимые символы (ZWSP и пр.) прозрачны,
   пробелы схлопываются только при СРАВНЕНИИ, не в координатах.
2. Перенос: двухуровневый дифф (SequenceMatcher по блокам → посимвольный внутри
   изменённых пар блоков — полный посимвольный дифф страницы дорог) → перенос
   диапазона через опкоды:
   - equal → сдвиг координат;
   - вставка СТРОГО ВНУТРИ диапазона → диапазон растягивается (маркер «липкий»
     внутри, как в редакторе DC);
   - вставка НА ГРАНИЦЕ → не входит (inclusive=false у annotation-марок);
   - удаление части → диапазон сжимается;
   - replace целиком внутри → накрывается (текст «перенабрали внутри выделения»);
   - от диапазона не осталось ни одного отображённого символа → lost.
   Перемещённый абзац = delete+insert → lost (как эталон). Никакого поиска.
3. Статус — по таблице выше; anchored_text пересчитывается всегда.

### Калибровка по «наземной истине»
В наших же снимках лежат НАСТОЯЩИЕ маркеры `ac:inline-comment-marker` чужих
inline-комментариев. Тест-фикстуры из пар версий реальных страниц позволяют
сверить: куда Confluence сам перенёс маркер ↔ куда переносит наш дифф.
(Инструментальный тест, не прод-логика.)

## 4. Этапы (каждый — зелёные тесты + отдельный коммит)

**Этап 1. Ядро anchoring.py + тесты.** Документная модель, перенос диапазонов,
статусные правила, догадка. Портирование всех сценариев test_highlight_projection
+ новые: вставка внутри/на границе, частичное удаление (сценарий пользователя
со словом «подзаголовок»), удаление+возврат слова (→ outdated, текст совпал →
остаётся outdated до подтверждения), перенос абзаца → lost, дубли текста,
таблицы/списки, ZWSP. Старый highlight_projection.py пока не трогаем.

**Этап 2. Сервис страниц.** `services/page_service.py`: вынос из routers/pages.py
логики снимков/refresh/promote/baseline (роутер — тонкий HTTP-слой; ~-300 строк).
Refresh переключается на anchoring.py. Alembic 009: + anchored_text, − xpath-поля;
одноразовый пересчёт: верификация якоря по цитате → точный поиск → lost.
Downgrade документирован (+ бэкап БД перед миграцией).

**Этап 3. API-чистка.** Удалить mark-lost / unmark-lost / mark-outdated (фронт
статусы больше не пишет). reanchor → тривиальный (original_quote := anchored_text).
create: серверная верификация «текст по координатам == цитата» (как
textSelection+matchIndex). Тест-обход маршрутов auth не забыть.

**Этап 4. Фронт: захват выделения.** Вынос из PageDetailPage: чистый
`selection/selectionAnchors.ts` (Range → блочные координаты; measureTextOffset,
трим-поправки) с jsdom-тестами + хук `useTextSelection` + компонент попапа.

**Этап 5. Фронт: рендер и статусы.** HighlightLayer → координатный рендерер
(мульти-mark по текст-нодам, ховер, outline остаются; вся поисковая каскадная
логика, findPartialRanges, statusSync, renderReport-статусы — удаляются).
PageDetailPage: убрать статусный эффект; счётчики/чипы читают статусы с сервера.
Защитный гард: текст под координатами != anchored_text → console.warn + рендер
без метки (диагностика рассинхрона, не статус).

**Этап 6. Фронт: панель.** Для outdated — вординг-дифф original_quote ↔
anchored_text («что изменилось»). Для lost — как сейчас: цитата и подсказка,
что привязка утрачена окончательно и тесты нужно перепривязать заново.

**Этап 7. Сквозная проверка и релиз.** Полный прогон (фронт+бэк), ручной
сценарий пользователя на живом стенде, changelog-записи, обновление CLAUDE.md
(правило статусов v1.5.9), актуализация памяти.

## 5. Риски и страховки
- Качество переноса = качество диффа. Страховки: двухуровневый дифф, фикстуры
  реальных страниц, калибровка по чужим маркерам, правило «сомнение → lost»
  (Brush: честный орфан лучше уверенной ошибки).
- Миграция БД: бэкап + документированный downgrade; точка отката — тег v.1.5.8.
- Поведенческие изменения для пользователя (яснее, но другие): статусы меняются
  только по refresh; авто-возврата из «Утрачено» нет — есть «Перепривязать».
