# Контекст проекта — ReqTrace

## Кто работает над проектом

QA-инженер на крупном e-commerce проекте. Работает в команде ручного тестирования (7–10 человек). На проекте также есть команда автоматизации, которая пишет snapshot-тесты и e2e-тесты на основе ручных проверок Manual QA. Проект ведётся по Agile.

---

## Цель

Индивидуальный план развития QA-инженера, направленный на рост в области обеспечения качества. Первый шаг — изучение методов оценки полноты покрытия требований. Конечная цель — создание инструмента для команды, который решит реальную проблему проекта.

---

## Проблематика на проекте

Требования хранятся в Confluence в виде страниц, каждая из которых относится к конкретному экрану приложения. Формат — таблица из двух колонок: слева макет из дизайна, справа поток текста с описанием требований. Требования не пронумерованы, но описаны достаточно чётко.

Тесты хранятся в XRay (Jira). Структура: папки по фичам, внутри — четыре типа проверок:
- **Инициализация** — откуда берутся данные для отображения (ответы сервера, внутренние данные приложения).
- **Запрос** — с какими параметрами и при каких условиях отправляются запросы на сервер.
- **Логика работы** — поведение экрана/элемента при взаимодействии пользователя (тапы, скроллы, свайпы).
- **Компоновка** — как выглядит экран/элемент в различных состояниях в зависимости от входных данных. Подробная декомпозиция на атомарные элементы. На основе этих проверок автоматизаторы пишут snapshot-тесты.

Внутри тестов в XRay есть ссылка на страницу Confluence, по которой написан тест.

**Основная боль:** частые изменения требований в Confluence приводят к тому, что тестовый репозиторий устаревает. Команда не может быстро ответить на вопрос «что именно актуализировать». Нет метрик покрытия требований. Нет матриц трассировки. Ориентироваться в большом репозитории тестов и большом объёме требований сложно.

## Инструментарий команды

- **Jira** — управление задачами.
- **XRay** — репозиторий тестов, прогоны.
- **Confluence Server** — хранение требований (зона ответственности аналитиков; QA может только оставлять inline-комментарии, не редактировать).

## Что уже сделано

### 1. Отчёт о методах оценки полноты покрытия требований

Файл: `methods-coverage-assessment.md`

Описаны 7 методов:
1. Requirements Traceability Matrix — матрица трассировки требований.
2. Code Coverage — покрытие кода.
3. Functional Coverage — покрытие функциональности.
4. Risk-Based Testing Coverage — покрытие на основе анализа рисков.
5. Test Design Techniques Coverage — покрытие на основе техник тест-дизайна.
6. Model-Based Testing Coverage — покрытие на основе моделей.
7. Acceptance Criteria Coverage — покрытие критериев приёмки.

Команда де-факто использует элементы методов 3 (покрытие функциональности), 4 (анализ рисков) и 5 (техники тест-дизайна через систему четырёх типов проверок).

### 2. Техническое задание на инструмент ReqTrace MVP

Файл: `technical-specification.md`

Инструмент для визуальной трассировки покрытия требований тестами. Позволяет загружать страницы Confluence, выделять произвольные фрагменты текста, привязывать к ним тест-кейсы из XRay и отслеживать изменения в требованиях.

---

## Ключевые решения по инструменту

### Стек
- Frontend: React + TypeScript
- Backend: Python + FastAPI
- БД: PostgreSQL
- Развёртывание: Docker Compose (3 контейнера) на Mac Mini в офисе

### Архитектурные решения

**Посимвольное выделение.** Пользователь выделяет произвольный фрагмент текста на странице (включая картинки и отдельные символы). Позиция сохраняется через XPath + символьное смещение. Дополнительно хранится текст фрагмента и контекст (100 символов до/после) для восстановления позиции при изменении структуры HTML.

**Снимки и baseline.** Содержимое страницы Confluence сохраняется как снимок (snapshot). Baseline — закреплённая версия, относительно которой оценивается покрытие и считается diff. После актуализации тестов пользователь закрепляет новый baseline.

**Проекция выделений.** При обновлении страницы выделения из baseline проецируются на новую версию. Статусы: `active` (текст не изменился), `outdated` (текст изменился — тесты требуют проверки), `lost` (текст не найден).

**Два режима просмотра.** «Покрытие» — подсветка выделений зелёным/жёлтым/красным. «Изменения» — классический diff добавленного/удалённого текста между baseline и актуальным снимком.

**Авторизация MVP.** Простая — по имени, без пароля. Для идентификации автора выделений.

**Многопользовательский доступ.** Все члены команды видят все выделения и привязки. Общее рабочее пространство.

**Интеграция с Confluence Server.** Через REST API (Basic Auth). Загрузка содержимого страницы, получение информации о версиях.

**Интеграция с Jira/XRay.** На этапе MVP — ручной ввод ключа теста (`PROJECT-123`). Инструмент формирует кликабельную ссылку по шаблону.

### Дизайн
Выполняется по дизайн-системе Surf. Файлы дизайна находятся в папке `Design/`. Ключевые характеристики:
- Светлый фон `#FFFFFF`.
- Зелёный акцент `#7AE05A`, тёмно-зелёный `#4DB830`.
- Glassmorphism: полупрозрачные карточки `rgba(255,255,255,0.8)`, `backdrop-filter: blur(20px)`.
- Радиальные градиентные блобы на фоне (lilac-pink, green, yellow-green).
- Границы `rgba(0,0,0,0.07)`.
- Скругления 14–24px для карточек, 100px для пилюль.
- Шрифт: `-apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif`.
- Layout: sidebar + header + content (паттерн admin-panel).
