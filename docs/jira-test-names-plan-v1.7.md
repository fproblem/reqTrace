# План v1.7.0 — названия тестов из Jira

Статус: **утверждён к проработке, реализация не начата** (ресёрч 2026-07-19).
Ветка `release/v1.7.0` открыта.

## 1. Задача и границы

Пользователь при привязке видит только ключ (`SI-12847`) — что это за тест,
приходится помнить или ходить в Jira. Нужно подтягивать из Jira **только
название теста** (поле `summary` задачи) и показывать его рядом с ключом:

- в панели привязки (список тестов) — «какой тест я только что прикрепил»;
- на экране «Тесты», ярус 2 — строка ключа становится читаемой без Jira.

**Сознательно НЕ входит** (границы, заданные пользователем): статусы
прогонов, комментарии, переходы, создание задач, двусторонняя связь — никакая
другая интеграция не нужна. Единственное допустимое расширение в будущем —
автокомплит ключей при вводе (ранее отклонён именно потому, что без Jira
дропдаун голых номеров неинформативен; названия его разблокируют).

## 2. Jira API — что известно

Тесты XRay — обычные задачи Jira; название = `summary`.

- **Точечно**: `GET /rest/api/2/issue/{KEY}?fields=summary` → `{fields:{summary}}`.
  404 — ключ не существует (опечатка или тест удалён). Работает и для
  «переехавших» задач: запрос по старому ключу отдаёт задачу с НОВЫМ key.
- **Батч**: `GET /rest/api/2/search?jql=issuekey in (K1,K2,…)&fields=summary&maxResults=100`.
  С непустым fields пагинация — до 100 задач на страницу (id-only отдал бы до
  5000, нам не подходит). ⚠ Известная засада: несуществующий ключ в
  `issuekey in (…)` по умолчанию роняет ВЕСЬ запрос ошибкой 400 —
  лечится `validateQuery=false` (мёртвые ключи молча выпадают из ответа).
  ⚠ Вторая засада: «переехавшая» задача возвращается в батче с новым ключом —
  сопоставление ответа с запрошенными ключами обязано быть по множеству
  «запросил − получил», остаток добирается точечными GET.
  **Обе засады проверить живым спайком на jira.surfstudio.ru — первый шаг
  реализации.**
- **Аутентификация**:
  - Jira **Data Center/Server 8.14+**: персональный токен (PAT),
    `Authorization: Bearer <token>` — токен наследует права пользователя,
    отзывается, не является паролем. ⚠ PAT НЕ работает через Basic.
  - Basic username/password на DC работает, но серия неудачных логинов
    включает CAPTCHA (elevated security check) и блокирует вход человека —
    та же LDAP-осторожность, что у ночных кред Confluence, только жёстче.
  - Jira **Cloud**: Basic `email:api_token`. На будущее — клиент абстрагируем,
    но v1.7.0 целится в корпоративный DC.

## 3. Креды: личный Jira-токен (PAT), опционально

Решение зеркалит модель Confluence-кред (v1.5.1): подключение личное, походы
в Jira — от имени участника.

- В `project_credentials` добавляется **опциональное** поле
  `jira_token_enc` (Fernet, тот же `CREDENTIALS_KEY`). UI — в модалке кред
  карточки проекта: поле «Jira-токен (необязательно)» с подсказкой, где его
  выпустить (профиль Jira → Personal Access Tokens), и живой проверкой
  (`GET /rest/api/2/myself`).
- **Реюз пароля Confluence НЕ делаем автоматически**: если LDAP общий —
  сработает, если нет — 401-серия ночью взведёт CAPTCHA и заблокирует
  человека. Единственное допустимое место пробы — явная кнопка «проверить»
  при вводе (одна попытка по клику человека). В v1.7.0 не делаем вовсе:
  PAT — 2 минуты у пользователя.
- Правила осторожности — как у Confluence-кред: 401 от Jira помечает токен
  invalid (`jira_token_status`), ночью invalid НЕ перепроверяется; чинится
  вводом нового токена в профиле.
- Без единого рабочего токена у проекта фича просто молчит: ключи
  показываются как сейчас. Деградация полная и бесшумная.

## 4. Хранение: таблица test_details

```
test_details
  id UUID PK
  project_id UUID FK projects ON DELETE CASCADE, index
  test_key   VARCHAR(64)   -- нормализованный (upper, как _norm_key)
  summary    TEXT NULL     -- название; NULL = ещё не тянули или не нашли
  fetch_result VARCHAR(16) -- ok | not_found | error
  fetched_at TIMESTAMPTZ
  UNIQUE (project_id, test_key)
```

- **Пер-проект**, не глобально: jira_base_url — свойство проекта; один ключ
  в разных проектах может жить в разных Jira.
- Название — общее для участников проекта (не персональные данные; команда
  и так живёт в одной Jira). Права Jira различаются → правило перезаписи:
  `ok` перезаписывает всё; `not_found`/`error` НЕ затирают существующий
  summary (бесправный участник не должен «стереть» имя, добытое коллегой).
- Ретеншн: при ночной синхронизации удаляются строки ключей, которых больше
  нет в привязках проекта (осиротевшие после отвязки/удаления).

## 5. Актуализация — по аналогии со страницами

Тесты меняются вслед за требованиями — названия не должны протухать.

1. **При привязке** (add_test_link): мгновенный точечный fetch кредами
   инициатора, best effort с коротким таймаутом (~3 с) — имя появляется в
   панели сразу; заодно честная валидация «такой тест существует»
   (404 → мягкое предупреждение в тултипе, ключ NOT_FOUND в базе; сама
   привязка создаётся в любом случае — как сейчас).
2. **Ночной прогон** (run_project, после страниц): DISTINCT ключи привязок
   проекта → батчи по 100 через search (validateQuery=false) → upsert;
   не вернувшиеся из батча — точечными GET (различить «переехал» и
   «не существует»). Кредами того же участника, что и прогон, при наличии
   у него токена; иначе — первого участника с рабочим токеном.
   Jira недоступна (VPN) → пропуск без порчи данных, дотянется следующей
   ночью/добором; отдельного статуса skip в журнале прогона НЕ заводим
   (названия — не критичный груз ночи).
3. **Нагрузка**: сотни ключей на проект = единицы запросов за ночь.

## 6. Отдача и отображение

- `GET /api/projects/{id}/tests`: `TestIndexEntry` + `summary` (join по
  test_details). Ярус 2: в строке аккордеона рядом с ключом — название
  серым текстом с эллипсисом («SI-12847 · Оплата картой: возврат средств»).
- `GET /api/pages/{id}/highlights`: `TestLink` + `summary`. Панель привязки:
  название второй строкой под ключом (11–12px, textSecondary, эллипсис).
- Фолбэк везде: summary нет → ровно текущий вид (только ключ).
- Нестандартные ключи (не `isLikelyJiraKey`) в Jira не запрашиваются вовсе —
  бэкенду нужно серверное зеркало проверки формата (сейчас она только на
  фронте, testKeyFormat.ts).

## 7. Риски (сводно)

| Риск | Мера |
|---|---|
| CAPTCHA-блокировка LDAP при Basic-переборе | только PAT/Bearer; 401 → invalid, ночью не ретраим |
| Мёртвый ключ роняет батч-JQL (400) | validateQuery=false + точечный fallback; живой спайк первым шагом |
| «Переехавшие» задачи возвращаются с другим ключом | сопоставление «запросил − получил», остаток точечно |
| Бесправный участник затирает имена | not_found/error не перезаписывают ok-summary |
| Jira Cloud (другая auth) | клиент абстрагирован (Bearer/Basic по конфигу кред); в v1.7.0 — DC |
| Секретность токена | Fernet тем же CREDENTIALS_KEY; в API токен наружу не отдаётся |
