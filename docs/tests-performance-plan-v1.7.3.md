# Производительность экрана «Тесты» — план v1.7.3

Статус: реализуется. Ветка `release/v1.7.3`.

## Проблема

Ярус 2 «Тестов» (`GET /projects/{id}/tests`) отдавал весь реверс-индекс одним
ответом: все ключи, все привязки каждого ключа, у каждой привязки — полная
цитата (с v1.6.5 не режется). Закрытому списку из этого нужно ~10%: ключ,
название, счётчики.

Замер на живой БД (26.07.2026, Burger King, 122 теста / 195 привязок):
ответ **91 878 байт**, ~13мс локально. Экстраполяция на 1000 тестов /
~3000 привязок: **~0.75–1 МБ** JSON, из которых ~80% — цитаты и UUID-ы
привязок. Плюс эндпоинт поднимал из БД `text_content` ВСЕХ привязок проекта,
включая непривязанные к тестам, а фронт рендерил все строки разом и
пере-фильтровывал их на каждый символ поиска.

Важно: названия из Jira загрузку НЕ тормозят — они читаются из локальной
`test_details` (ночная синхронизация), в Jira при открытии экрана походов нет.

## Решение (вариант «лёгкий список + привязки по раскрытию»)

Отклонённые альтернативы: серверная пагинация+поиск (ломает мгновенный
клиентский поиск, нужна от ~10k+ тестов — в бэклоге), виртуализация списка
(добавлять только если замер после этого решения покажет боль рендера).

**Бэкенд:**
- `GET /projects/{id}/tests` — ЛЁГКИЙ список: по ключу `summary`,
  `jira_status`, счётчики `active/outdated/lost`, `pages_count`; сверху
  `pages_covered` (для строки сводки). Цитаты не поднимаются из БД вовсе
  (select без `text_content`). Агрегация по-прежнему в Python (FakeSession).
- `GET /projects/{id}/test-links?key=…` — привязки одного ключа с полными
  цитатами (`TestKeyLinks`), сортировка (page_title, excerpt). Нормализация
  ключа продублирована в SQL (`upper(trim(...))`), чтобы не поднимать чужие
  цитаты. key — query-параметр: нестандартные ключи бывают с «/».
  Пустой список — 200, не 404 (ключ могли отвязать, пока строка открыта).

**Фронтенд (`ProjectTestsPage`):**
- Кэш `linksByKey` на время жизни экрана; единый эффект загрузки по
  появлению ключа в `expanded` (клик и `?key=`-прибытие — один путь);
  ошибка сворачивает строку (повторный клик = повторная попытка).
- Поиск/фильтры/сортировка НЕ меняются: они и раньше смотрели только на
  ключ и название — по-прежнему клиентские, мгновенные, с подсветкой.
- URL-контракт не тронут: `?q=`, `?f=`, `?key=`.

**UX ожидания (спека пользователя, 26.07.2026):** раскрытие открывается сразу
на высоту РОВНО одной строки привязки; первые 200мс — пусто (быстрые ответы
не мигают, порог v1.7.1), дальше fade-ом появляется лоадер
(`RefreshIcon` + «Подтягиваем привязки…»); когда ответ пришёл и контент выше
плейсхолдера — блок ПЛАВНО дорастает до реального размера, без рывка.
Реализация: `TreeReveal` (раскрытие/сворачивание) → новый общий
`components/AnimatedHeight.tsx` (ResizeObserver внутреннего блока + transition
height 200мс, reduced-motion уважается) → LinksPending | строки привязок.

## Замеры до/после (живая БД, Burger King 122 тестов / 195 привязок)

- Список ДО: **91 878 байт** (~13мс локально).
- Список ПОСЛЕ: **12 683 байта** (~12мс) — **×7.2 легче**; объём больше не
  зависит от длины требований. На 1000 тестов разрыв растёт до ~×10
  (~150КБ против ~1МБ).
- Привязки одного ключа (3 привязки, полные цитаты): 2 017 байт, ~19мс.

## Бэклог по теме

- Серверная пагинация и поиск — порог «реверс-индекс от ~10k тестов».
- Виртуализация списка — по результатам замера рендера после v1.7.3.
- `useDeferredValue` для поискового ввода — если ввод начнёт подтормаживать
  на многотысячных списках.
